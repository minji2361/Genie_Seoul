## 배경 및 목적

운영진이 코드 수정 없이 (1) 30일 이상 경과한 인터뷰·대시보드 데이터를 검토·정리하고, (2) 홈 진입 팝업의 문구·이미지·노출 여부를 직접 관리할 수 있도록 관리자 전용 화면을 마련한다. 이 문서는 개발 착수 전 확인용 기획서이며, 실제 스키마·코드 변경은 이 문서가 확정된 뒤 진행한다.

## 현재 구조 (As-Is)

기획에 들어가기 전 확인한 기존 코드 기준 사실관계.

**인증 & 접근권한**
`ADMIN_ID` / `ADMIN_PASSWORD` 단일 계정을 모든 코치가 공유 로그인. 역할 구분이 없어 로그인한 사람은 `/dashboard`, `/interview`, `/admin`에 동일하게 접근 가능.

**`/admin` 페이지**
이미 존재. 인터뷰·대시보드 탭으로 전체 목록 조회(이름 검색만) 가능하나 삭제·수정 기능은 없음.

**데이터 모델**
`participant`(대시보드) ← 검사 테이블 7종(cascade delete) · `int_interviews`(독립, 대시보드와 무관). 둘 다 `created_at` 보유. 서명·검사 이미지는 Storage 버킷에 별도 저장되어 **DB row를 지워도 파일은 남는다.**

**코치 삭제 (기존)**
대시보드·인터뷰 목록에 이미 삭제 버튼 존재. 브라우저 `confirm` 1회 → 즉시 하드 삭제, 본인이 등록한 데이터로 범위 한정. Storage 파일 정리는 빠져 있음(기존 이슈).

**홈 팝업**
`HomePopup.tsx`에 이미지 경로·문구가 하드코딩. "오늘 하루 안 보기"만 localStorage로 제어할 뿐, DB 연동이나 ON/OFF 스위치 없음 — 끄려면 코드 수정·배포 필요.

## 권한 모델 (신규)

코치 로그인과 별개로 관리자 전용 로그인을 신설한다. 관리자 세션일 때만 `/admin` 접근 및 데이터 삭제·팝업 수정이 가능하다.

| 항목 | 코치 로그인 | 관리자 로그인 |
|---|---|---|
| 접근 화면 | /dashboard, /interview | /admin (좌 두 화면 접근 불가) |
| 데이터 조회 범위 | 본인이 등록한 데이터만 | 전체 코치의 데이터 |
| 네비게이션 노출 | Dashboard / Interview | Admin 링크는 관리자 세션에서만 노출 |

구현 시 `middleware.ts`의 `/admin`, `/api/admin/**` 매처가 로그인 여부뿐 아니라 관리자 세션인지까지 확인하도록 조건을 추가한다.

## 데이터 관리

30일 이상 경과한 인터뷰·대시보드 데이터를 관리자가 검토해서 유지·삭제를 결정하는 화면.

### 조회 화면 — 통합 리스트 + 필터

기존 "인터뷰/대시보드 탭 분리" 대신 하나의 리스트에서 상단 필터로 범위를 좁혀 조회한다. 필터를 좁힌 뒤 그 범위 안에서 선택·삭제하는 구조라 일괄삭제 시 의도한 범위만 지워졌는지 확인하기 쉽다.

- **유형**: 전체 / 인터뷰 / 대시보드
- **기간(경과)**: 1주 이내 / 2주 이내 / 3주 이내 / 그외(3주 초과)
- **공통 컬럼**: 구분, 이름, 담당 코치, 등록일, 경과일, 유지여부, 체크박스

> "그외"는 3주(21일) 초과 전체를 뜻하며, 30일 경과 삭제 후보가 여기 포함된다는 전제로 정리했다 — 이 정의가 맞는지는 [확인 필요 사항](#확인-필요-사항) 참고. 상세 항목(나이·MBTI·지역 vs 생년월일·스트레스요인 등)은 행 클릭 시 펼쳐보기로 분리한다.

### 삭제 로직 — 코치 vs 관리자

| 항목 | 코치 삭제 | 관리자 삭제 |
|---|---|---|
| 범위 | 본인 데이터만 | 전체 코치 데이터 |
| 시점 제한 | 없음 (현행 유지) | 주로 30일 경과 검토 목록에서 사용 |
| 확인 단계 | 1단계 (현행 `window.confirm` 유지) | 2단계 확인 + 대상 건수·이름 노출 |
| 실행 방식 | 즉시 하드 삭제 | 즉시 하드 삭제 + Storage 파일 정리 |
| `retain` 체크된 항목 | 삭제 차단 | 일괄삭제 자동선택에서 제외 |

### "유지" 플래그 (신규)

`participant`, `int_interviews`에 `retain boolean default false` 컬럼을 추가한다. 관리자가 목록에서 체크하면 `retain = true`가 되어 이후 코치도 해당 항목을 삭제할 수 없다.

**적용(enforcement) 지점이 두 곳으로 나뉜다.** `int_interviews` 삭제는 서버 API를 거치므로 라우트에서 `retain = false` 조건을 추가하면 된다. 반면 `participant` 삭제는 브라우저에서 Supabase anon client로 테이블을 직접 호출하므로, 프론트 코드만으로 막으면 개발자도구로 우회될 수 있다 — 실제 방어는 **RLS 정책 자체에 `retain = false` 조건을 넣는 방식**(`using (auth.uid() = counselors and retain = false)`)으로 DB 레벨에서 강제해야 한다.

### 다중 선택 & 일괄삭제

- 목록 행별 체크박스 + 헤더 "전체 선택" → 1건 이상 선택 시 "선택 삭제" 버튼 활성화.
- "한달 지난 건 일괄삭제" 버튼: `기간=그외` + `retain=false` 조건으로 자동 전체선택 후 동일한 확인 플로우로 합류.
- 확인 모달에 "인터뷰 N건, 대시보드 M건, 총 N+M건"처럼 구분별 건수를 표시해 실행 전 범위를 한 번 더 확인시킨다.

### 스키마 변경 요약

| 테이블 | 컬럼 | 설명 |
|---|---|---|
| participant | `retain boolean default false` | true면 코치 삭제 차단, 일괄삭제 대상에서 제외 |
| int_interviews | `retain boolean default false` | 동일 |

## 팝업 관리

코드 수정·배포 없이 문구·이미지·노출 여부를 관리자 화면에서 제어한다.

| 필드 | 용도 |
|---|---|
| `title` | 팝업 제목 |
| `description` | 본문 문구(줄바꿈 배열) |
| `image_url` | 팝업 이미지, 관리자 업로드 → Storage(`popup-images` 버킷 신설) |
| `is_active` | ON/OFF — false면 홈에서 컴포넌트 자체가 렌더링되지 않음 |

비로그인 방문자도 봐야 하므로 인증이 필요 없는 공개 조회 API를 별도로 두고, `HomePopup.tsx`가 하드코딩 상수 대신 이 API 값을 읽어 렌더링하도록 바꾼다. "오늘 하루 안 보기"(localStorage)는 관리자 ON/OFF와 별개 레이어로 그대로 유지한다.

## 진행 순서 제안

1. **권한 모델** — 관리자 전용 로그인 신설. 이후 모든 관리자 기능의 전제가 되므로 가장 먼저 진행.
2. **팝업 관리** — 스키마 1개, 화면 1개로 범위가 작고 독립적이라 빠르게 검증 가능.
3. **데이터 관리** — `retain` 컬럼, RLS 정책, 통합 리스트·필터, 다중선택·일괄삭제까지 포함되어 범위가 가장 큼.

## 결정 로그

논의 중 확정된 의사결정.

- **관리자 화면 접근 권한 모델** → 별도 관리자 계정 신설 (확정)
- **데이터 삭제 방식** → 2단계 확인 후 즉시 하드 삭제 (소프트 삭제·배치 스케줄러 없음) (확정)
- **코치 삭제 범위 — 시점 제한을 둘지** → 현행 유지(제한 없음) + `retain` 체크 시에만 차단 (확정)
- **코치 삭제 확인 단계 강화 여부** → 현행 유지 — 1단계 `confirm` (확정)
- **관리자 삭제 — 다중 선택 가능 여부** → 체크박스 다중 선택 + "한달 지난 건 일괄삭제" 단축 버튼 (확정)
- **관리자 조회 화면 구조** → 탭 분리 대신 통합 리스트 + 유형/기간 상단 필터 (확정)

## 확인 필요 사항

공유 후 확인되면 다음 항목까지 반영해서 개발에 들어간다.

1. **"그외" 기간 필터의 정확한 정의** — 3주(21일) 초과 전체로 가정(30일 경과 삭제 후보를 포함하는 구간). 다른 의미(예: 전체 기간 무관)였다면 정정 필요.
2. **관리자 로그인 방식** — 코치 로그인과 같은 화면에서 자격만 다르게 둘지, `/admin/login`을 별도 페이지로 분리할지는 개발 단계에서 결정.
3. **기존 코치 삭제 경로의 Storage 정리 누락** — 지금도 참가자·인터뷰 삭제 시 서명 이미지 등 Storage 파일이 안 지워지는 기존 이슈가 있음 — 이번 기획과 별개로 정리할지 확인 필요.
